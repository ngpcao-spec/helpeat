# Séparation des inscriptions HOME Reviews et Helpeat

## Audit avant la première migration

Les deux applications utilisent Supabase `ihuztjkblywzjdruusdj` et la même identité dans `auth.users`. Le trigger `on_auth_user_created` appelle actuellement `private.handle_new_user()`, qui crée le profil, une organisation, son adhésion de propriétaire et des préférences de notification via `private.provision_home_user(uuid)`.

La RPC `public.ensure_home_user()` était absente. Le helper historique accepte un UUID et les rôles `anon` et `authenticated` héritaient du droit SQL de l’exécuter. Le correctif retire ces droits. Les politiques RLS de production réservent les profils à leur propriétaire et les organisations, adhésions, établissements et avis à leurs membres. Les modifications d’organisations et d’établissements restent soumises aux rôles existants.

## Déploiement progressif

Les scripts restent hors de `supabase/migrations`. Les appliquer individuellement, dans l’ordre ci-dessous, en enregistrant leur version dans l’historique Supabase. La migration Helpeat `20261124082946` est déjà enregistrée en production. La [branche d’alignement HOME Reviews](https://github.com/ngpcao-spec/home-reviews-demo/tree/codex/helpeat-journal-history) contient sa copie pour l’historique partagé.

La phase 1 est appliquée en production. Supabase a enregistré `home_reviews_self_provisioning` sous la version `20261124162149` à partir du fichier validé `20261124084826_home_reviews_self_provisioning.sql`. Utiliser la version enregistrée pour l’alignement de l’historique partagé.

La sauvegarde chiffrée du 24 novembre 2026 à 06 h 28 UTC couvre le projet partagé. Le reçu confirme la restauration et la comparaison de 335 tables dans une instance isolée du réseau. Ce point de récupération précède la première migration Auth. [Restauration de la sauvegarde de production](https://github.com/ngpcao-spec/home-reviews-demo/actions/runs/45342716542)

En l’absence de sauvegarde gérée, exporter les rôles, le schéma et les données suivant la procédure Supabase avec un accès Postgres préexistant. Conserver les fichiers et leurs empreintes SHA‑256 sur un stockage protégé. Restaurer dans une instance isolée et protégée, vérifier `auth.users`, `auth.identities`, les profils, adhésions, établissements, avis et repas, ainsi que le trigger et les politiques RLS. Consigner le point de récupération, l’heure de la restauration, ses résultats et le commit HOME Reviews de retour arrière. Garder les données de production dans l’environnement protégé. [Vérifier les sauvegardes Supabase](https://supabase.com/docs/guides/platform/backups) · [Exporter et restaurer avec la CLI](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)
2. Appliquer [le provisionnement sécurisé](20261124084826_home_reviews_self_provisioning.sql). La RPC utilise exclusivement `auth.uid()`, n’accepte aucun argument et refuse les sessions anonymes. Elle conserve les adhésions existantes, refuse de rétablir une adhésion retirée et sérialise les premières initialisations par utilisateur. Le trigger historique reste actif pendant cette phase. Contrôler les droits effectifs et l’absence du schéma privilégié `home_reviews_onboarding` dans les schémas exposés par la Data API.
3. Appliquer [le patch HOME Reviews](home-reviews-onboarding.patch) au commit candidat testé et publier ce commit corrigé. Si la branche principale a avancé, relancer les vérifications sur la nouvelle combinaison avant publication. Vérifier le déploiement Pages, la mise à jour d’une PWA déjà installée, la connexion d’un compte existant et d’un nouveau compte **dans HOME Reviews**, puis les établissements, avis et rôles attendus. Une session sans organisation déclenche explicitement la RPC au démarrage de HOME Reviews. Toute application détenant une session valide peut appeler ce point d’entrée pour le même utilisateur. La sécurité repose sur l’identité Auth et les droits du compte.
4. Garder Helpeat en démo avec son pilote restreint pendant les étapes 1 à 3. Toute création dans `auth.users` avant la bascule déclenche encore le provisionnement historique, même si le compte vient de Helpeat. Les redirections OAuth et les métadonnées client ne dispensent pas du trigger. Une organisation créée pendant cette phase restera présente après la migration.
5. Appliquer [la séparation des inscriptions](20261124102903_separate_helpeat_signup.sql). Après validation de la transaction, reconnecter une session de contrôle et vérifier que la définition du trigger initialise uniquement `public.profiles`. La première initialisation HOME Reviews crée ensuite l’organisation, l’adhésion et les préférences de notification. Tester les comptes existants et un compte neuf dans chaque application. Pour le compte neuf Helpeat, ajouter temporairement le callback exact `http://127.0.0.1:4173/helpeat/?mode=real`. Compiler sur le poste de validation avec `VITE_HELPEAT_ENABLE_REAL=true` et la clé publique Supabase dans `VITE_HELPEAT_SUPABASE_PUBLISHABLE_KEY`, puis servir le build avec `npm exec -- vite preview --host 127.0.0.1 --port 4173 --strictPort`. Confirmer que l’inscription crée seulement le profil, puis ouvrir HOME Reviews avec le même compte et vérifier qu’une seule organisation apparaît. Arrêter le serveur local et retirer le callback temporaire à l’issue du test.
6. Attendre la confirmation explicite d’ouverture de Helpeat. Retirer la restriction du pilote dans un déploiement séparé, ajouter le nouveau callback exact en conservant les callbacks existants et revalider Google dans Safari et dans la PWA. Le parcours [pilote](https://ngpcao-spec.github.io/helpeat/?mode=pilot) et la [démo](https://ngpcao-spec.github.io/helpeat/) servent aux vérifications pendant le déploiement.

## Retour arrière

Après la première migration, le frontend HOME Reviews précédent peut être republié si nécessaire. Il reste compatible avec le trigger historique et les droits restreints du helper.

Après la deuxième migration, fermer d’abord le parcours d’inscription Helpeat de validation et retirer son callback temporaire. Rétablir le trigger historique avec [rollback-trigger.sql](rollback-trigger.sql) en gardant le frontend HOME Reviews compatible et la RPC sécurisée. Vérifier avec une nouvelle inscription de test depuis HOME Reviews que le trigger crée à nouveau une organisation. Les comptes créés pendant la séparation gardent leur profil et pourront déclencher la RPC en ouvrant HOME Reviews. En cas d’incident sur les données, restaurer d’abord le point de récupération dans un environnement isolé pour examiner l’écart et préserver les écritures plus récentes.

## Reproduire les contrôles

- `npm test` dans Helpeat vérifie les migrations et le retour arrière dans PostgreSQL embarqué, les droits d’exécution, les adhésions existantes et l’isolation du journal.
- Le [workflow Supabase jetable](../../.github/workflows/validate-isolated-auth.yml) utilise de vraies sessions Auth et la Data API avec des identités fictives. Il couvre la restauration d’un export logique synthétique dans une seconde base, le provisionnement avant et après la bascule, deux sessions concurrentes, le même identifiant dans les deux applications, l’isolation des données et le retour arrière. Les identités de test portent des claims Google simulés par le hook local.
- Sur une copie du commit HOME Reviews à déployer, vérifier `git apply --check` puis appliquer le patch et lancer `npm ci` et `npm run build`. Installer `embedded-postgres@17.12.0-beta.19` dans un répertoire temporaire séparé et renseigner son chemin dans `HISTORY_NATIVE_PACKAGE` pour inclure le test de concurrence sur PostgreSQL local. Exécuter ensuite `npm exec -- vitest run --maxWorkers=2 --testTimeout=45000 --hookTimeout=90000`. Cette commande exécute la suite générale avec deux workers. Les assertions et les délais explicitement fixés dans les fichiers de test s’appliquent.
- Lancer aussi `npm exec -- playwright test --config playwright.auth.config.ts`. Playwright simule le fournisseur Google et vérifie les parcours compte neuf, compte existant, reconnexion et démarrage iPhone. Les essais avec le fournisseur Google sur des appareils physiques restent une étape du déploiement du nouveau flux.
