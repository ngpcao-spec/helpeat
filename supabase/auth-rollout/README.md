# Séparation des inscriptions HOME Reviews et Helpeat

## Audit de production

Les deux applications utilisent Supabase `ihuztjkblywzjdruusdj` et la même identité dans `auth.users`. Le trigger `on_auth_user_created` appelle actuellement `private.handle_new_user()`, qui crée le profil, une organisation, son adhésion de propriétaire et des préférences de notification via `private.provision_home_user(uuid)`.

La RPC `public.ensure_home_user()` est absente. Le helper historique accepte un UUID et les rôles `anon` et `authenticated` héritent encore du droit SQL de l’exécuter. Le correctif retire ces droits. Les politiques RLS de production réservent les profils à leur propriétaire et les organisations, adhésions, établissements et avis à leurs membres. Les modifications d’organisations et d’établissements restent soumises aux rôles existants.

## Déploiement progressif

Les scripts restent hors de `supabase/migrations`. Les appliquer individuellement, dans l’ordre ci-dessous, en enregistrant leur version dans l’historique Supabase. La migration Helpeat `20261124082946` est déjà enregistrée en production. La [branche d’alignement HOME Reviews](https://github.com/ngpcao-spec/home-reviews-demo/tree/codex/helpeat-journal-history) contient sa copie pour l’historique partagé.

1. Avant toute modification de production, identifier un point de récupération couvrant les données applicatives et Auth. En l’absence de sauvegarde gérée, produire un dump avec la procédure Supabase et le conserver sur un stockage approuvé. Vérifier la restauration dans une instance isolée et protégée, puis contrôler l’intégrité de `auth.users`, `auth.identities`, des profils, adhésions, établissements et repas. Consigner l’identifiant du point de récupération et le commit HOME Reviews servant de version de retour arrière. [Vérifier les sauvegardes Supabase](https://supabase.com/docs/guides/platform/backups) · [Exporter et restaurer avec la CLI](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)
2. Appliquer [le provisionnement sécurisé](20261124084826_home_reviews_self_provisioning.sql). La RPC utilise exclusivement `auth.uid()`, n’accepte aucun argument et refuse les sessions anonymes. Elle conserve les adhésions existantes, refuse de rétablir une adhésion retirée et sérialise les premières initialisations par utilisateur. Le trigger historique reste actif pendant cette phase. Contrôler les droits effectifs et l’absence du schéma privilégié `home_reviews_onboarding` dans les schémas exposés par la Data API.
3. Publier uniquement [le patch HOME Reviews](home-reviews-onboarding.patch), préparé sur `82db1a114ebcc5b4f76b72029e54b0af01b0c8c5`. Vérifier le déploiement Pages, le démarrage d’une PWA déjà installée après mise à jour, la connexion d’un compte existant et d’un nouveau compte, puis les établissements, avis et rôles attendus. Une session sans organisation déclenche explicitement la RPC au démarrage de HOME Reviews. Toute application qui détient une session valide pourrait appeler ce même point d’entrée pour l’utilisateur connecté. La sécurité repose sur l’identité Auth et les droits du compte, sans déduction de l’origine de l’appel.
4. Appliquer [la séparation des inscriptions](20261124102903_separate_helpeat_signup.sql) après validation des étapes précédentes. Le trigger garde son attache et initialise seulement `public.profiles` avec le même identifiant Auth et un nom d’affichage. Les métadonnées utilisateur servent uniquement à ce libellé. La première initialisation HOME Reviews crée ensuite l’organisation, l’adhésion et les préférences de notification. Après cette étape, vérifier les comptes existants et le cycle complet d’un compte de test neuf dans chaque application avant toute ouverture.
5. Attendre la confirmation explicite d’ouverture de Helpeat. Retirer la restriction du pilote dans un déploiement séparé, ajouter le nouveau callback exact en conservant les callbacks existants et revalider Google dans Safari et dans la PWA. Le parcours [pilote](https://ngpcao-spec.github.io/helpeat/?mode=pilot) et la [démo](https://ngpcao-spec.github.io/helpeat/) servent aux vérifications pendant le déploiement.

## Retour arrière

Après la première migration, le frontend HOME Reviews précédent peut être republié si nécessaire. Il reste compatible avec le trigger historique et les droits restreints du helper.

Après la deuxième migration, rétablir d’abord le trigger historique avec [rollback-trigger.sql](rollback-trigger.sql). Vérifier qu’une nouvelle inscription de test crée à nouveau une organisation et que seules les sessions éligibles peuvent appeler la RPC. Garder le frontend compatible pendant cette vérification. Le retour arrière conserve les données. Les comptes créés pendant la séparation gardent leur profil et pourront déclencher la RPC en ouvrant HOME Reviews. En cas d’incident sur les données, restaurer d’abord le point de récupération dans un environnement isolé pour examiner l’écart et préserver les écritures plus récentes.

## Reproduire les contrôles

- `npm test` dans Helpeat vérifie les migrations et le retour arrière dans PostgreSQL embarqué, les droits d’exécution, les adhésions existantes et l’isolation du journal.
- Le [workflow Supabase jetable](../../.github/workflows/validate-isolated-auth.yml) utilise de vraies sessions Auth et la Data API avec des identités fictives. Il couvre deux sessions concurrentes, le même identifiant dans les deux applications, la lecture et les modifications autorisées, ainsi que l’isolation des profils, avis, établissements et repas. Les identités de test portent des claims Google simulés par le hook local.
- Sur une copie de HOME Reviews au commit indiqué, appliquer le patch puis lancer `npm ci`, `npm test`, `npm run build` et `npm exec -- playwright test --config playwright.auth.config.ts`. Playwright simule le fournisseur Google et vérifie les parcours compte neuf, compte existant, reconnexion et démarrage iPhone. Les essais avec le fournisseur Google sur des appareils physiques restent une étape du déploiement du nouveau flux.
